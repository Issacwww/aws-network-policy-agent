# DNS Policy：本轮交付与阅读导览

本轮是可复现的 POC 和团队评审材料，不是 GA 实现。英文正文在 [en/](en/)，中文只保留阅读导览，避免两份设计逐渐不一致。

**最重要的结论：** 单独 DNAT 在 NodeLocal NOTRACK 下会漏掉 DNS 授权；单独 TPROXY 在 IPVS Service DNS 下也会漏掉授权。新增的最小组合——Service 解析器用 DNAT，其他解析器用 TPROXY——在本地三种 kube-proxy 模式下通过了全部 20 项业务测试及 NodeLocal UDP/TCP 测试。推荐带这个组合去做 EKS 验证，尚未证明 EKS 无需代码调整。

## 建议先读设计，再看证据和计划

### 1. [整体设计](en/technical-design.md)

- **第 1 节：用户能观察到什么。** DNS 必须独立获准；成功响应要等授权写入完成。时序图就是整份设计的主线。
- **第 2 节：为什么要比较拦截方式。重点读。** 解释 proxy 在 NPA 容器中的位置、DNAT/TPROXY 分别完成哪些步骤，以及为什么推荐组合。新增成本是解析器地址分类、规则维护和权限，不是零成本兼容。
- **第 3 节：谁记住 DNS 授权。** 多个域名共享 IP 时，不能简单覆盖一条 map；生产需要记录每个授权的来源和到期时间。第一遍只需理解这个原因。
- **第 4 节：规则顺序。重点读。** 保留你指定的 CNP 书写顺序作为待团队确认的行为；没有把它误称为标准 NetworkPolicy 的行为。PE/CPE 不变仍是约束，顺序来源是待解决的实现依赖。
- **第 5 节：失败、TTL 和重启。重点看表。** 区分 POC 已验证的新连接撤权，与尚未决定的已有连接处理。也说明哪些故障保证还没实现。
- **第 6 节：安全、指标、发布。** 解释源身份变化、为什么无法可靠按 domain 给应用包归因，以及默认启用前有哪些条件。

### 2. [POC 报告](en/poc-report.md)

- **开头与第 1 节：看结论和完整矩阵即可。** DNS 返回成功与后续流量获准是两项不同检查。
- **第 2 节：重点读失败原因。** DNAT、NodeLocal、TPROXY、IPVS 的相互作用；解释组合方案如何补足，同时保留 Service-IP 共绑等未验证边界。
- **第 3 节：代码改了什么。** 方便代码评审定位新写的传输逻辑和沿用的移植代码。
- **第 4 节：环境与证据。** 原始 JSON、镜像、内核、版本都可追溯，不需要第一遍逐条读。
- **第 5 节：重点读限制。** 不把 kind 成功当作 EKS、IPv6、SG 或完整 CNP 已支持。

要在内部电脑继续，直接看 [复现与 EKS 交接说明](../../test/dns-policy-poc/README.md)。kind 的 metadata/CNI adapter 和 cluster-admin 测试清单不能部署到 EKS。

### 3. [威胁模型](en/aws-network-policy-agent-threat-model.md)

- **安全摘要与范围：** 不可信 Pod 的 DNS 数据进入高权限节点组件，再变成网络授权，这是新增的核心信任边界。
- **威胁表：重点读前三项及解析器信任。** 恶意解析器、跨 Pod/IP 复用、陈旧或部分授权，可能造成隔离失效；另列资源耗尽、raw socket 权限和 SG 身份变化。
- **最后的验证门槛：** 哪些测试和 AppSec 评审必须提前做。安全假设尚待确认，因此这是条件化评审草案，不是安全批准。

### 4. [Milestones](en/milestones.md)

- **关键路径：重点读。** 本地 POC → EKS 验证 → 正确的授权核心 → 故障/兼容完善 → 发布。
- **里程碑 0–4：** 每段包含结果、范围、排除项、验收、测试、安全/ORR、依赖和证据。可先只读每段开头的 outcome。
- **条件分支表：重点读。** 组合方案、CNP 顺序来源、已有连接立即撤权、SG strict，会怎样改变工作量和依赖。
- **时间：** 假设两名全职工程师、已有 AWS 环境和评审支持，暂估 10–19 周，包含组合方案的预留；不含外部审批/发布排队。它是待校准的计划假设，不是交付承诺。

## 本轮需要评审的内容

优先确认组合拦截是否作为下一轮 EKS 验证方向、已有连接的 TTL/删除语义，以及可信解析器的边界。CNP 书写顺序继续保持“待团队批准”；PE/CPE 不变和原解析器转发保持你已批准的约束。
